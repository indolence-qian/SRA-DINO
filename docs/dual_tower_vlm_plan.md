## 当前已经恢复的内容

- `run_exp.sh` 默认 `BASE_ARCH=clip_dino`，转到已有 `train_mara_visa.sh`。
- 保留原 `train.py`、CLIP prompt、DINO/HFA、检测头、MARA 的学习逻辑；不回滚数值修复。
- 原一阶段单卡、MARA 双卡 DDP、跨数据集测试双卡分配的方式保持不变。
- 一阶段语义锚点仍沿用原脚本按资源文件存在与否决定的默认设置。若做历史严格复现，必须固定权重、锚点配置、数据与预处理，而不能只依赖当前默认值。
- 单塔/VLM 代码保存在 `run_exp_dino_single.sh`，可独立复现，不删除权重或实验结果。
- 默认双塔拒绝单塔 checkpoint 和 VLM 阶段开关，防止旧命令误跑。
- 已新增 `run_exp_dual_vlm.sh`：冻结双塔导出 → 双卡直接 VLM 区域复核 → 固定校准评估。
- 该新入口实现下文 P1 的首版无参考实验，不经过 MARA；双塔 VLM 蒸馏仍未实现，也没有新的真实 GPU 实验结果。

## 为什么不是把现有 VLM 开关打开就行

代码中的双塔主要是 DINO 视觉表征与 CLIP 文本语义对齐；不要把它理解为必须并行运行两个视觉编码器。
`tools/utils_up.py::get_anomaly_map` 已输出跨模态分层概率、正常/异常相似度、margin、awareness 和全局 margin。
`tools/mara_evidence.py::build_mara_evidence` 可拼接语义图和语义全局向量，但双塔目前并不产生这些 VLM 语义值。

旧 `build_vlm_decision_cache.py`、`train_vlm_distiller.py` 只创建 DINO 单塔检测器；
`train_mara.py::apply_base_runtime_config` 也只对单塔语义头启用语义通道。
接入双塔需要独立实现双塔 teacher-input 导出、学生头训练、checkpoint 存取和训练/测试一致的语义通道注册，不能只改一个架构字符串。

上一轮截图里 Attempt/Refine/Reject 均为零，按现有推理逻辑意味着没有选择修正。
这不是 VLM 必然无用的证据，也不是关闭安全门就能解决的问题。
现有单塔蒸馏头只追加 MARA 证据，不改变 Base 概率，因此它的收益完全受制于 MARA 是否动作。

## 建议路线：先验证 VLM 候选复核，再决定是否蒸馏和接入 RL

### P0：固定双塔基础模型

优先复用此前表现较好的双塔 checkpoint。用同一预处理评估 Base 与 Base+MARA。
记录 STOP 概率、修正尝试数、实际执行数和候选真实收益；强制一次修正只作诊断，不当成部署策略。
在源域训练/验证划分上选择配置，目标测试集不用于早停、选 epoch 或选融合权重。

### P1：双塔候选 ROI + VLM 复核，不经过 MARA

建议给冻结的 Qwen3-VL-8B-Instruct-FP8 输入：原图、合规正常参考、候选裁剪及少量有标识的双塔证据图。
没有合法同类正常参考时，应明确标注参考缺失或使用无参考提示，不能把待测图自身伪装成正常参考。
候选来自分层 disagreement、高异常响应和低置信区域；加入少量随机/低响应区域检查候选遗漏，避免永远看不到 Base 的漏检。
单独比较有/无热图提示，检查 VLM 是否只是重复 Base 判断。

输出以候选区域的“缺陷/正常/不确定”、缺陷类型、候选排序为主，不要求 VLM 自由绘制像素掩码。
保留双塔的像素定位，仅对候选区域或图像分数做有界校准。
区域级文本框不能直接视为高质量像素真值；VLM 自报 confidence 也必须在源域验证集上校准，不能直接当概率。

先做几百张、包含正常/异常和多个源类别的 pilot，报告候选召回、ROI 判断质量、误报减少与新增漏检。
再分别报告图像 AUROC、像素 AUROC、PRO、F1，不能把图像级收益当成定位收益。
如果 VLM 的直接复核都没有稳定增益，就暂停蒸馏和 RL 接入，而不是继续扩大系统。

### P2：只有 P1 成立后，蒸馏为独立轻量校准头

冻结双塔基线，利用源域可用标签和经验证的 teacher 信号训练候选排序/校准头。
要求该头在无 MARA 的条件下就可输出修正结果，并做完全相同结构但无 VLM 监督的对照。
先确认学生保留了 teacher 的收益，再把它作为 MARA 的额外证据。
不让所有辅助信息都只能经过 STOP/REFINE 决策才影响输出。

## 推荐消融与决策标准

| 对照 | 目的 |
| --- | --- |
| 固定双塔 Base | 确认恢复的基线 |
| 双塔 + 原 MARA | 区分策略本身的收益/退化 |
| 双塔 + 无 VLM 的同结构校准头 | 排除仅增加参数/额外标签带来的收益 |
| 双塔 + 直接 VLM 候选复核（无 MARA） | 判断 teacher 本身是否提供新增信息 |
| 双塔 + VLM 蒸馏校准头（无 MARA） | 衡量蒸馏损失及部署价值 |
| 双塔 + 已验证校准头 + MARA | 最后判断 RL 的额外价值 |

直接 VLM 复核意味着推理时使用 8B 模型，应单列时延和硬件成本，不能与无 VLM 部署混报。
源域训练使用的正常参考不能来自未声明可用的目标域标注；使用目标域正常参考时应单列为不同协议。
真实标签 Oracle 只用于诊断候选潜力，不能进入推理或作为保证可实现的性能上界。
建议使用多个随机种子和逐类别结果，避免单次/单类别收益决定结论。

## 两张 24 GB GPU 的资源安排

此前日志只证明单个 FP8 模型加载约 10.31 GiB，不等于双塔、VLM、激活和 KV 缓存共驻就一定能运行。
优先采用分时方案：先运行双塔导出候选与紧凑证据，释放双塔进程；再让两张卡各自运行一个 VLM worker 分片复核；最后卸载 VLM，用双卡训练学生/MARA。
这样可继续使用现有独立 VLM conda 环境，不要求把 vLLM 安装到训练环境，也不要求扩大模型。
沿用仅图片、单请求和像素上限配置；实际峰值显存、速度及输出质量仍需 pilot 测量。

官方依据：
- [Qwen3-VL-8B-Instruct-FP8 模型卡](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct-FP8)：提供多模态模型和 vLLM 推理方法，不构成工业异常检测涨点保证。
- [vLLM 0.11 显存控制](https://docs.vllm.ai/en/v0.11.0/configuration/conserving_memory.html)：并发、上下文、多模态输入和 CUDA Graph 的显存配置。

结论：双塔后加入 VLM 在工程上可行，但应定位为“区域复核/校准教师”，先证明不依赖 MARA 的独立增益。当前已实现 P1 直接复核的独立入口；P2 蒸馏与 RL 接入仍须等待实验结果。
